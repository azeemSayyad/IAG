# Step 0.4 — Database Design

## Database Choice: PostgreSQL

### Why PostgreSQL

| Requirement | How PostgreSQL Delivers |
|-------------|----------------------|
| ACID Transactions | Full ACID compliance — critical for booking integrity and slot locking |
| Relational Integrity | Foreign keys, constraints, cascades ensure data consistency |
| Row Locking | `SELECT ... FOR UPDATE` prevents double-booking natively |
| JSON Support | `jsonb` columns for flexible AI metadata, prompts, and conversation context |
| Scalability | Supports read replicas, partitioning, connection pooling |
| Full-Text Search | Built-in search for leads, conversations, notes |
| Extensions | pg_vector for future AI embeddings, pg_cron for scheduled jobs |
| Multi-Tenancy | Efficient filtering on `tenant_id` with partial indexes |
| Mature Ecosystem | Excellent tooling: SQLAlchemy, Alembic, pgAdmin, Postico |

### Why NOT Other Databases

| Alternative | Reason for Rejection |
|-------------|---------------------|
| MySQL | Weaker locking semantics, no native JSON indexing |
| MongoDB | Relational data (leads → appointments → agents) needs joins and constraints |
| SQLite | Single-writer limitation, no concurrency for production |
| DynamoDB | Vendor lock-in, complex relational queries |

## Connection Architecture

```
Application Servers
        ↓
    PgBouncer (Connection Pooler)
        ↓
    PostgreSQL Primary (Writes)
        ↓
    PostgreSQL Read Replicas (Reads)
```

### Connection Pool Settings

- Pool size: 20 connections per worker
- Max connections: 200 total
- Pool mode: Transaction-level
- Idle timeout: 300 seconds

## Multi-Tenancy Strategy

### Shared Database, Shared Schema

Every tenant's data lives in the same tables, isolated by `tenant_id`.

```
┌─────────────────────────────────────────┐
│  leads table                            │
│  ┌──────────┬───────────┬─────────────┐ │
│  │ tenant_a │ tenant_b  │ tenant_c    │ │
│  │ row 1    │ row 101   │ row 201     │ │
│  │ row 2    │ row 102   │ row 202     │ │
│  └──────────┴───────────┴─────────────┘ │
└─────────────────────────────────────────┘
```

### Tenant Isolation Rules

1. Every table with business data has a `tenant_id` column
2. Every query includes `WHERE tenant_id = :tenant_id`
3. Application middleware injects `tenant_id` from JWT automatically
4. No raw SQL without tenant filter — enforced at ORM level
5. Index on `(tenant_id, ...)` for all high-traffic queries

## Naming Conventions

| Element | Convention | Example |
|---------|-----------|---------|
| Tables | snake_case, plural | `leads`, `appointments` |
| Columns | snake_case | `first_name`, `created_at` |
| Primary Keys | `id` (UUID) | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` |
| Foreign Keys | `{referenced_table}_id` | `lead_id`, `agent_id` |
| Indexes | `idx_{table}_{columns}` | `idx_leads_tenant_status` |
| Timestamps | `created_at`, `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` |
| Soft Deletes | `deleted_at` | `NULL` = active, timestamp = deleted |

---

## UUID vs Auto-Increment

**Decision: UUIDs**

Why:
- No sequential ID guessing (security)
- Safe for distributed systems
- No collision across microservices
- Can generate IDs client-side

Implementation:
```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

---

## Timestamp Strategy

All timestamps use `TIMESTAMPTZ` (timezone-aware UTC).

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

Application stores everything in UTC. Frontend converts to user's timezone.

---

## Soft Delete Strategy

Tables that need soft deletes:
- `leads` — preserve history
- `users` — preserve audit trail
- `agents` — preserve appointment history
- `tenants` — preserve billing records

Implementation:
```sql
deleted_at TIMESTAMPTZ DEFAULT NULL
```

Queries filter: `WHERE deleted_at IS NULL`

---

## Index Strategy

### Always Index

- `tenant_id` on every table
- Foreign keys (`lead_id`, `agent_id`, `conversation_id`)
- Status columns used in WHERE clauses
- Timestamp columns used in range queries

### Composite Indexes

- `(tenant_id, status)` — filtered list queries
- `(tenant_id, created_at)` — time-range queries
- `(agent_id, start_time)` — calendar lookups
- `(lead_id, created_at)` — conversation history

## Migration Strategy

Use Alembic for schema migrations.

```
/migrations
    /versions
        001_create_tenants.py
        002_create_users.py
        003_create_leads.py
        ...
```

Rules:
- Never drop columns in production — soft delete or rename
- Always have a rollback migration
- Test migrations on staging before production
- Back up database before running migrations
